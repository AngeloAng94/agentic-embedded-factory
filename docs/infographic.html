EmbedFactory · mappa del sistema · control plane v1

Dal requisito al firmware verificato.

Una software factory conversazionale per firmware embedded: scheletro deterministico → patch validate → build reale → riparazione guidata dagli errori del compilatore → validazione dell'artefatto. Zephyr è l'implementazione completa oggi; FreeRTOS è un modello di stato già previsto, senza finta prontezza.

verification · REAL / SIMULATED / NOT_AVAILABLE verdict · SUCCESS / FAILURE / UNKNOWN nessun READY senza evidenza
01

Cosa risolve

il problema è la fiducia, non la generazione
problema

Firmware “scritto bene” che non è mai stato compilato

Un LLM può produrre codice plausibile e totalmente non compilabile: nessuno se ne accorge finché non tocca il toolchain.

EmbedFactory: ogni modifica passa da un build reale; l'output del compilatore è l'unica verità.
problema

Setup manuale di skeleton e board

CMakeLists, prj.conf, main.c, board name: lavoro ripetitivo e fonte di errori silenziosi a ogni nuovo progetto.

EmbedFactory: skeleton deterministico, versionato, con board scelta solo tra quelle che il doctor ha davvero elencato.
problema

Nessuna traccia di chi ha cambiato cosa

Patch applicate “a memoria”, stato del progetto indistinguibile tra “sembra pronto” e “è stato costruito”.

EmbedFactory: versioni immutabili con patch, autore, motivo e verdetto di build; ripristino di qualsiasi versione.
problema

Non si sa cosa manca per poter buildare

Errori generici, toolchain assenti, runner spento: l'utente non sa se il problema è il codice o l'ambiente.

EmbedFactory: doctor reale + control plane che dice cosa non è pronto e perché.

03

Come funziona — la pipeline

un turno, sette passaggi verificabili
01

Skeleton deterministico · nessun LLM

Il progetto nasce da template fissi: CMakeLists.txt, prj.conf, src/main.c, README.md, .gitignore, con board e RTOS richiesti. La prima versione è sempre ricostruibile e non dipende da un modello linguistico.

IN →nome, rtos, board, requisito
OUT →albero file + versione v1
02

Contesto e prompt server-side

Retrieval della knowledge base entro un budget, poi un prompt strutturato: progetto, RTOS, board, MCU, file correnti, patch già applicate, ultimo build reale e richiesta utente.

IN →requisito + stato progetto
OUT →prompt completo (tracciato)
03

Piano del modello un solo oggetto JSON

Il modello non risponde a testo libero: restituisce { summary, creates, patches, requestBuild, answerOnly }. La risposta viene estratta e validata; se il provider è irraggiungibile il turno fallisce esplicitamente: nessun file creato, nessun file modificato, nessun build avviato.

IN →prompt
OUT →piano di patch o answer-only
ERR →LLM_BAD_RESPONSE · PLAN_EMPTY
04

Validazione patch tutto-o-niente

I file esistenti si modificano solo con unified diff a 3 righe di contesto: se il contesto non combacia byte per byte l'intera operazione è rifiutata (PATCH_FAILED) e non viene scritto nulla. I path sono confinati a src/, include/, drivers/, app/, tests/, boards/, scripts/ e ai file radice ammessi.

IN →piano + contenuto corrente
OUT →file aggiornati + versione immutabile
05

Build reale il runner è l'unico che compila

Dispatch HTTP al runner, che esegue davvero west build -b <board> -d build -p auto nella working directory corretta. Torna exit code, comando, stdout/stderr, artefatti e memoria linker. Convex non può lanciare processi: senza runner il risultato è NOT_AVAILABLE, mai un build finto.

IN →progetto + board + toolchain
OUT →REAL · exit 0
OUT →REAL · errore compilatore
06

Ciclo di riparazione max 3 tentativi

In caso di FAILURE gli errori reali di GCC/linker rientrano nel prompt con l'istruzione di correggere solo quei punti, non di riscrivere il file. Ogni tentativo è un build reale. Alla fine: BUILD FAILED o REPAIR LIMIT REACHED, con la cronologia completa.

IN →stderr + exit code del build
OUT →patch correttiva → rebuild
07

Validazione artefatto l'evidenza

L'ELF viene ispezionato senza dipendenze esterne: magic number, header ELF32/64, endianness, architettura (ARM, RISC-V, Xtensa, ARC), entry point, dimensione e SHA-256. La memoria FLASH/RAM arriva dal report del linker. Il manifest di export porta con sé board, toolchain e verdetto.

IN →zephyr.elf + report linker
OUT →ELF ARM · sha256 · FLASH/RAM
04

Output

cosa resta all'utente
out

Artefatti del prodotto

Progetto firmware versionato
File reali, più la storia v1…vn: contenuto, autore, motivo, patch e verdetto di build. Ogni versione è ripristinabile.
Evidenza di build reale
Comando, exit code, durata, stdout/stderr e artefatto ispezionato.
es. zephyr.elf · ELF · ARM · sha256:… · FLASH 41 236 B / 256 KB · RAM 9 536 B / 64 KB
valori emessi dal runner su una macchina con toolchain
Manifest + export ZIP
ZIP costruito davvero nel browser (file + README + manifest) e inizializzazione Git opzionale.
{ rtos, board, toolchain, verification, verdict }
Stato onesto del progetto
verified solo dopo un build reale riuscito; altrimenti unverified. Le righe del vecchio motore simulato restano LEGACY · UNVERIFIED.
non-out

Quello che non produce (per scelta)

Nessun “deploy” o flash sulla board
HIL, flashing e test su hardware non sono implementati: non esiste una UI che li simuli.
Nessun verdetto senza esecuzione
Un runner che risponde “successo” con exit code diverso da 0 viene declassato a UNKNOWN.
Nessuna importazione di firmware esistente
L'entry point “Existing Firmware” è visibile ma disabilitato: Coming soon, nessuna schermata finta.
Nessuna board “supportata” per decreto
La lista board viene dal doctor. Se non è verificabile, la UI scrive UNKNOWN / NOT VERIFIED.

Control plane

tre livelli, una sola fonte di verità
livello 1 · orientamento

Dashboard

  • Welcome + due ingressi: New Firmware e Existing Firmware (disabilitato).
  • System status a colpo d'occhio: AI, build runner, Zephyr, FreeRTOS, toolchain.
  • First-run checklist non bloccante: collega AI → verifica runner → toolchain Zephyr → FreeRTOS.
  • Ogni riga di stato apre il dettaglio in Environment.
/dashboard
livello 2 · diagnosi

Environment

  • AI: provider, modello, connessione, ultimo controllo reale.
  • Runner: URL, stato, latenza, tool riportati da GET /health.
  • Zephyr: tabella doctor (west, cmake, ninja, python, dtc, ZEPHYR_BASE, SDK, arm-zephyr-eabi, board) e output grezzo.
  • FreeRTOS: Not configured finché non esiste un doctor reale.
  • Run diagnostics esegue davvero il doctor via runner.
/environment
livello 3 · configurazione

Settings

  • AI/LLM: sette variabili, più Test connection con una generazione reale.
  • Build runner: URL e token, più Test runner con GET /health.
  • Secret mostrati solo come Configured / Not configured.
  • General: modelli e limiti già esistenti, nessuna impostazione duplicata.

06

La regola di onestà

due campi, nessuna eccezione
verificationexit codeverdictcosa vede l'utente
REAL0SUCCESS Build eseguito, artefatto validato, progetto verified.
REAL≠ 0FAILURE Errori del compilatore reali + tentativi di riparazione.
SIMULATED—UNKNOWN Eredità del motore rimosso: LEGACY · UNVERIFIED.
NOT_AVAILABLE—UNKNOWN reason: toolchain unavailable — “west” is not installed or not in PATH
  • SUCCESS esiste solo con REAL e exitCode = 0.
  • Un progetto diventa verified solo dopo un build reale riuscito.
  • Un probe memorizzato viene invalidato appena cambia la configurazione che ha misurato.
  • Secret: Configured / Not configured. Mai in chiaro, mai in una risposta API, mai in un log, mai in localStorage.
  • Se manca un pezzo, la UI dice cosa e perché; non riempie il vuoto con un badge verde.
  • “Dimmi cosa è pronto, cosa non lo è, e perché.”
07

Architettura

chi può eseguire cosa
client

Web · React 19 + Vite

Legge solo stato normalizzato. Nessun secret, nessun toolchain, nessun build.

backend

Convex · auth + dati

Query/mutation con proprietà verificata, azioni node per LLM e dispatch. process.env qui.

esecuzione

Runner · Bun HTTP

Unico componente che esegue west, cmake, ninja, dtc. Endpoint: health, doctor, build, git, analyze, export.

verità

Toolchain nativa

Zephyr SDK, arm-zephyr-eabi, board di west boards. L'unica fonte di un SUCCESS.

Perché il runner esiste: un runtime serverless non può avviare processi nativi. Invece di simulare un build, il sistema sposta l'esecuzione dove il toolchain vive davvero e degrada in modo esplicito: senza runner → NOT_AVAILABLE; senza doctor → UNKNOWN; il progetto esportato resta comunque buildabile in locale.
bun runner/index.ts doctor — questa macchina può buildare firmware?
bun runner/index.ts verify --board nucleo_l476rg — fallimento → riparazione → successo, reale
bun runner/index.ts serve --port 8790 — il runner che alimenta la web app
bun test · bunx tsc -b --noEmit · bunx convex dev --once
